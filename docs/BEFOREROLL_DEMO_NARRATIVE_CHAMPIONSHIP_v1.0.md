## Preregistered assessment framework

Registered in this report before detailed concept design or comparative selection on 27 October 2026 (workspace date). The report will retain this framework when findings are completed. This is a local, auditable decision framework, not an independent preregistered model benchmark.

Hard gates: (1) no suggestion becomes authentic permission or fulfillment; (2) the core story uses actual source inventory → Decide → three-field Extract → review, not preselected clauses or hardcoded answers; (3) it fits current functionality or explicitly bounded later work; (4) it uses fictional, rights-safe material; (5) the visible outcome remains useful with unresolved authority.

Compare all concepts on the same twelve questions: sponsor/rubric fit; domain credibility; documentary conflict; consequential Clocked contribution; honest AI-off contrast; current-app demonstrability; safety/provenance; first-view comprehension; visual/narrative interest; memorable operational outcome; implementation/testing effort; live-demo failure risk.

Use evidence-backed ordinal judgments: **supported**, **plausible but requires verification**, **weak/high risk**, or **unknown**. Do not invent additive numeric scores or assume endpoint count proves quality. Explain each trade-off and cite the domain, sponsor or implementation evidence that changes it.

Selection order: first reject gate failures; then prioritize (a) a visible causal Clocked contribution and useful coordinator outcome, (b) first-view comprehension, (c) existing technical feasibility and manageable test risk. Domain credibility is mandatory throughout. Visual appeal breaks a genuine tie; it cannot rescue a confusing or unimplemented workflow. Run a sensitivity check: state which different priority would make another concept preferable. A hybrid wins only if it reduces cognitive/implementation burden compared with its components.

At registration, no recommendation was selected. The findings and selection below were added after source research. The framework above has not been changed to favor the selected concept.

## 3. Sponsor/product analysis: what a Clocked-native story should prove

The [official developer guide](https://clocked.rezolve.ai/developers), [API introduction](https://clocked.rezolve.ai/docs) and endpoint references below are **undated living documentation**, read on 27 October. Their audience is developers building backend workflows: supply a source and named questions/fields, receive typed data, then implement application behavior and uncertainty handling. The guide explicitly separates decision probabilities, extraction confidence and evidence-relative verification support; they are not interchangeable reliability scores.

Clocked's relevant differentiation is a direct contract for judgments and source reads rather than requiring this application to parse free-form chat prose. That is a product/API distinction, not proof that ordinary language-model APIs could never implement similar behavior or that Clocked is always more accurate/faster/cheaper.

| Capability | Documented behavior | BeforeRoll use / decision |
|---|---|---|
| [Decide](https://clocked.rezolve.ai/docs/decide) | Named yes/no (`noul`), choice, multiselect and ordered score questions; probabilities; typed outputs | **Implemented** two-question semantic activity/permission-claim reading. | [Extract](https://clocked.rezolve.ai/docs/extract) | Literal text values and exact positions; scalar/list/record options; confidence and absent values | **Implemented** fixed three-list prerequisite contract. Deterministic decoder independently checks original substrings and absolute offsets |

| [Compare](https://clocked.rezolve.ai/docs/compare) | Pairwise same/overlapping/conflicting/unrelated relationships, optional source evidence | **Not implemented provider integration.** Potential later cross-document investigation; not legal precedence or authenticity |

Source spans use **zero-based Unicode codepoints, end exclusive**. Native images have a different response contract without these text offsets/probabilities. A screenshot or scanned document must not be presented as if its image response had passed the existing text-span decoder. The documented source limits are admission caps, not accuracy or exhaustiveness guarantees. Extract documentation currently has inconsistent list-limit wording (table up to 256 versus prose/developer guide 32); existing lists cap at five/six and are below both. A future expanded contract must resolve that gap instead of inferring an unlimited obligation list. [Extract reference](https://clocked.rezolve.ai/docs/extract), [developer guide](https://clocked.rezolve.ai/developers).

### Is a third endpoint worth it?

**Optional candidate: Fill for a documentary-status review record**, not for rewriting existing task titles. User problem: a coordinator still has to distinguish a document that *claims to issue* an activity variation from a request, or find that a referenced supporting instrument is absent. A bounded Fill schema could return a typed claimed document role (`issued_claim` / `request` / `historical_reference` / `not_established`), verbatim stated scope/reference phrases with `infer:false`, and explicit uncertainty. BeforeRoll could use that record to open a specific **“locate and verify referenced instrument”** review, retaining the original text and refusing authority promotion. This adds information not represented by the current relevance/grant probabilities and three prerequisite lists.

Smallest falsification: freeze a small matched fictional packet containing one claimed-issued instrument, an unsigned request, an old reference and a missing supporting reference; compare the current workflow with Fill-assisted records. Reject the addition if it creates unsupported status assertions, loses exact spans, adds no genuinely distinct next action, or confuses “document says issued” with “verified issued.” It must improve human work, not only earn a third badge. Complexity/risk: medium-to-high—new decoder, provenance, review projection, current/history handling, ambiguity and browser acceptance. **Do not make hero readiness depend on it. No Fill build or paid experiment is authorized by this report.** Decide/Extract remains the default Batch B scope unless the owner explicitly selects this additional increment.

Compare is a potentially worthwhile later investigation of conflicting instruments, but requires separate validation and cannot make an unsigned request supersede an issued document. Rerank is premature for a handful of units. Generating a handover paragraph with Fill would mostly duplicate the existing dossier and introduce avoidable generated-text risk. Adding every endpoint, native vision or a provider pipeline solely for breadth would dilute the strongest existing evidence.

### Why semantic intelligence is useful here

The practical problem is the gap between **what the scene plans to do** and **what the paperwork says must exist for that kind of activity**. A scene may say “actor unfolds the chart”; a condition may regulate “direct manipulation of loaned printed material.” A keyword-only warning for “equipment” or “consent” does not establish that relationship. A generic location filter cannot reliably separate a case-only interview from physical handling in the same room. A typed extractor can then return the actual required instrument, protection and person instead of an invented checklist.

The coordinator still needs to verify the source, scope and real-world readiness. The useful outcome is a specific investigation handover: **which scene, what to locate/check, why, exact source and what remains unresolved**. Do not promise that the model discovers all missing documents or that no candidate means no requirement.

Authority sources establish that the coordination problem is credible; they do **not** establish BeforeRoll's market size, measured time savings, prevention of shutdowns, willingness to pay or adoption. No production-professional interview or field trial was performed. Stronger impact language would require real-user research.
